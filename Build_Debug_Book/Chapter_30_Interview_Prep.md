## 1. Rapid-Fire Concepts

```
  ┌──────────────────────────────────────────────────────────┐
  │                                                           │
  │  Build System (Ch 1-10):                                 │
  │  ┌──────────────────────────────────────────┐            │
  │  │ Q: What's the difference between         │            │
  │  │    depends on and select in Kconfig?      │            │
  │  │ A: depends on = "I need X to be enabled  │            │
  │  │    for me to appear in menuconfig."       │            │
  │  │    select = "When I'm enabled, I force X │            │
  │  │    on (dangerous — can violate X's deps)"│            │
  │  │                                          │            │
  │  │ Q: obj-y vs obj-m vs obj-$(CONFIG_FOO)?  │            │
  │  │ A: obj-y = built-in, obj-m = module,     │            │
  │  │    obj-$(CONFIG_FOO) = conditional        │            │
  │  │                                          │            │
  │  │ Q: clean vs mrproper vs distclean?       │            │
  │  │ A: clean = object files. mrproper =      │            │
  │  │    + .config + generated files. distclean │            │
  │  │    = + editor backups + patches           │            │
  │  │                                          │            │
  │  │ Q: What does CROSS_COMPILE= set?         │            │
  │  │ A: Prefix for all toolchain binaries:    │            │
  │  │    gcc→aarch64-linux-gnu-gcc, ld→...-ld  │            │
  │  │                                          │            │
  │  │ Q: initrd vs initramfs?                  │            │
  │  │ A: initrd = block device in RAM (ext2).  │            │
  │  │    initramfs = cpio archive → tmpfs      │            │
  │  │    (no filesystem driver needed)         │            │
  │  │                                          │            │
  │  │ Q: DT overlay vs full DTS?              │            │
  │  │ A: Overlay (.dtbo) patches base DTB at   │            │
  │  │    runtime. Used for add-on boards /     │            │
  │  │    HATs without replacing full DTS.      │            │
  │  │                                          │            │
  │  │ Q: What is System.map?                   │            │
  │  │ A: Symbol→address map generated by nm.   │            │
  │  │    Used by build tools. Runtime: kallsyms │            │
  │  │    is embedded in kernel for oops decode. │            │
  │  └──────────────────────────────────────────┘            │
  │                                                           │
  │  Tracing (Ch 11-22):                                     │
  │  ┌──────────────────────────────────────────┐            │
  │  │ Q: ftrace overhead when disabled?        │            │
  │  │ A: Zero — all call sites patched to NOPs │            │
  │  │    at boot. Dynamic binary patching.     │            │
  │  │                                          │            │
  │  │ Q: eBPF verifier purpose?                │            │
  │  │ A: Static analysis ensures: no infinite  │            │
  │  │    loops, no OOB memory, type safety,    │            │
  │  │    guaranteed termination. Programs are   │            │
  │  │    PROVEN safe before execution.         │            │
  │  │                                          │            │
  │  │ Q: perf sampling mechanism?              │            │
  │  │ A: PMU counter overflows → NMI → kernel  │            │
  │  │    captures IP + metadata → ring buffer  │            │
  │  │    → userspace reads.                    │            │
  │  │                                          │            │
  │  │ Q: kprobe vs tracepoint?                 │            │
  │  │ A: kprobe = dynamic, any address, INT3   │            │
  │  │    breakpoint, fragile across versions.  │            │
  │  │    Tracepoint = static, predefined,      │            │
  │  │    stable API, static key (faster).      │            │
  │  │                                          │            │
  │  │ Q: BPF_MAP_TYPE_RINGBUF vs              │            │
  │  │    PERF_EVENT_ARRAY?                     │            │
  │  │ A: Ringbuf = single shared buffer,       │            │
  │  │    globally ordered, back-pressure.      │            │
  │  │    perf_event = per-CPU, no cross-CPU    │            │
  │  │    ordering, drops on overflow.          │            │
  │  │                                          │            │
  │  │ Q: CO-RE means?                          │            │
  │  │ A: Compile Once, Run Everywhere. eBPF    │            │
  │  │    compiled once, libbpf relocates field │            │
  │  │    offsets at load time using BTF.       │            │
  │  └──────────────────────────────────────────┘            │
  │                                                           │
  │  Debugging (Ch 23-29):                                   │
  │  ┌──────────────────────────────────────────┐            │
  │  │ Q: KASAN vs KFENCE for production?       │            │
  │  │ A: KASAN = 100% detection, 2-3x overhead │            │
  │  │    (dev/test only). KFENCE = sampling,   │            │
  │  │    <1% overhead (production OK).         │            │
  │  │                                          │            │
  │  │ Q: What does Sparse check?               │            │
  │  │ A: Address space annotations: __user     │            │
  │  │    (security-critical), __iomem, __rcu,  │            │
  │  │    __bitwise (endianness). Type mix-up   │            │
  │  │    detection.                            │            │
  │  │                                          │            │
  │  │ Q: Oops error code 0x0002 means?        │            │
  │  │ A: Bit 0=0 (not-present page), bit 1=1  │            │
  │  │    (write access). → Write to unmapped   │            │
  │  │    page in kernel mode.                  │            │
  │  │                                          │            │
  │  │ Q: Why does kdump need kexec?            │            │
  │  │ A: Can't trust the crashed kernel's I/O. │            │
  │  │    kexec boots a fresh crash kernel in   │            │
  │  │    reserved RAM, which safely dumps      │            │
  │  │    the original kernel's memory.         │            │
  │  │                                          │            │
  │  │ Q: syzkaller key innovation?             │            │
  │  │ A: Coverage-guided (KCOV) + syscall      │            │
  │  │    grammar awareness. Generates valid-ish│            │
  │  │    syscall sequences that reach deep     │            │
  │  │    kernel paths. + KASAN catches the bugs│            │
  │  └──────────────────────────────────────────┘            │
  └──────────────────────────────────────────────────────────┘
```

## 2. Architecture Scenario: Debugging a Production Issue

```
  ┌──────────────────────────────────────────────────────────┐
  │                                                           │
  │  Scenario: Production server has intermittent latency   │
  │  spikes (p99 jumps from 1ms to 50ms every few hours)   │
  │                                                           │
  │  Investigation workflow:                                 │
  │  ┌──────────────────────────────────────────┐            │
  │  │ 1. perf stat — IPC, cache-miss rates    │            │
  │  │    → normal IPC but high cache-misses    │            │
  │  │    during spikes? Hardware issue.         │            │
  │  │    → low IPC + high context switches?    │            │
  │  │    Scheduling problem.                   │            │
  │  │                                          │            │
  │  │ 2. bpftrace scheduler latency:           │            │
  │  │    tracepoint:sched:sched_wakeup +       │            │
  │  │    sched_switch, histogram latency       │            │
  │  │    → p99 runqueue wait time?             │            │
  │  │                                          │            │
  │  │ 3. offcputime — where is the process     │            │
  │  │    sleeping/blocking?                    │            │
  │  │    → lock contention? I/O wait?          │            │
  │  │    → mutex_lock stack traces?            │            │
  │  │                                          │            │
  │  │ 4. biosnoop — block I/O latency per req  │            │
  │  │    → SSD doing GC? Journal commit?       │            │
  │  │                                          │            │
  │  │ 5. Perfetto trace — correlate scheduler, │            │
  │  │    CPU frequency, IRQs, I/O on timeline  │            │
  │  │    → frequency drop during spike?        │            │
  │  │    → long IRQ handler blocking?          │            │
  │  │                                          │            │
  │  │ 6. Flame graphs — on-CPU + off-CPU       │            │
  │  │    comparison during normal vs spike     │            │
  │  │    → new function appearing in spike?    │            │
  │  └──────────────────────────────────────────┘            │
  └──────────────────────────────────────────────────────────┘
```

```
  │  │ → GCC/Clang → Linker → vmlinux →        │            │

  │                                                           │
  │  LAYER 2: Static Analysis (before execution)             │
  │  ┌──────────────────────────────────────────┐            │
```

## 4. Common Pitfalls

```
  ┌──────────────────────────────────────────────────────────┐
  │                                                           │
  │  1. "I'll just use printk for everything"               │
  │     → Use pr_debug + dynamic debug for verbose output   │
  │     → Use tracepoints/eBPF for production observation   │
  │     → printk is for lifecycle events and errors only    │
  │                                                           │
  │  2. "KASAN found no bugs, so the code is correct"       │
  │     → KASAN only detects bugs that are EXERCISED        │
  │     → Need good test coverage + fuzzing to trigger them │
  │     → KCSAN for races, UBSAN for UB — different classes │
  │                                                           │
  │  3. "I'll enable all debug options in production"       │
  │     → KASAN = 2-3x slowdown (dev only)                 │
  │     → lockdep = 30% overhead (dev only)                 │
  │     → KFENCE = <1% (production OK)                      │
  │     → eBPF tracing = <5% when enabled (production OK)  │
  │                                                           │
  │  4. "ftrace has always-on overhead"                      │
  │     → NOPs when disabled = literally zero overhead      │
  │     → Only active tracers have cost                     │
  │                                                           │
  │  5. "kprobes are as stable as tracepoints"              │
  │     → kprobes break across kernel versions             │
  │     → Tracepoints are maintained API                    │
  │     → Use tracepoints first, kprobes as last resort     │
  │                                                           │
  │  6. "QEMU debugging is the same as real hardware"       │
  │     → Timing different (no real DMA, interrupts)        │
  │     → Some bugs only appear on real HW (races, DMA)    │
  │     → QEMU great for logic, not timing-dependent bugs  │
  └──────────────────────────────────────────────────────────┘
```

## Interview Questions

**Q1: Design a debugging infrastructure for a fleet of 10,000 embedded Linux devices.**
**A:** Architecture: (1) **Always-on baseline** (every device): KFENCE (< 1% overhead, catches memory bugs over time). pstore/ramoops (preserves crash logs across reboot). Structured kernel logging to /dev/kmsg → shipped to central log aggregation (Elasticsearch/Loki). Panic watchdog → auto-reboot + save vmcore to eMMC partition. (2) **On-demand deep tracing** (enabled per-device): Perfetto daemon + trace config pushed from fleet management server. Request trace → device records 10s Perfetto trace (ftrace events + atrace) → uploads to cloud → analyze with trace_processor SQL. eBPF programs pushed to devices for specific investigations (CO-RE compiled once, runs across kernel versions via BTF). (3) **Crash analysis pipeline**: pstore crash logs auto-uploaded → central server matches against kernel builds → auto-runs `scripts/decode_stacktrace.sh` → alerts to engineering. For severe/unknown crashes: kdump configured with `makedumpfile -d 31` (compressed, filtered) → upload vmcore → auto-analyze via crash scripts (`bt`, `log`, slab statistics). (4) **Pre-deployment**: CI with KASAN + KCSAN + UBSAN builds. syzkaller fuzzing for driver interfaces. KUnit + kselftest for regression testing. Sparse + Coccinelle for static analysis.

**Q2: Compare the entire kernel debugging tool ecosystem — when to use what?**
**A:** Decision tree: (1) **Compile-time bugs** → Sparse (address spaces, endian), Coccinelle (patterns), compiler warnings (-Wall -Wextra). (2) **Logic bugs during development** → GDB over QEMU (full control, single-step), KUnit (unit test functions), printk/pr_debug (quick checks). (3) **Memory bugs** → KASAN (development, 100% detection), KFENCE (production, sampling). (4) **Concurrency bugs** → KCSAN (data races), lockdep (deadlocks, lock ordering). (5) **Undefined behavior** → UBSAN (shifts, overflow, alignment). (6) **Performance analysis** → perf stat (quick metrics), perf record + flame graphs (hotspot analysis), bpftrace one-liners (ad-hoc investigation), Perfetto (cross-layer timeline). (7) **Production tracing** → eBPF/BCC tools (execsnoop, biolatency, tcplife), ftrace events, Perfetto. (8) **Crash analysis** → Oops decode (faddr2line, decode_stacktrace.sh), kdump/crash (post-mortem), pstore (crash logs). (9) **Finding unknown bugs** → syzkaller (fuzzing), syzbot (continuous). Key principle: each tool has its sweet spot. The expert's skill is knowing which tool to reach for first.

## Summary

- Build: Kconfig → Kbuild → cross-compile → DT/ACPI → initramfs → boot
- Static: Sparse + Coccinelle + compiler warnings → catch bugs before execution
- Sanitizers: KASAN (memory), KCSAN (races), UBSAN (UB), KFENCE (production)
- Logging: printk → dynamic debug → dmesg → pstore → netconsole
- Tracing: ftrace → tracepoints → kprobes → perf → eBPF → Perfetto
- Crash: oops decode → kdump/crash → GDB/KGDB → addr2line
- Testing: KUnit → kselftest → LTP → syzkaller → KernelCI
- Production: KFENCE + eBPF + pstore + Perfetto (all low-overhead)
