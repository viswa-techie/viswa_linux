# Chapter 4: Virtual Memory Concepts

## Chapter Overview

Virtual memory is the single most important abstraction in modern operating systems. It gives each process its own private, contiguous address space, regardless of how physical memory is actually organized. This chapter explains virtual memory from first principles, covering why it exists, how it works conceptually, and how Linux implements it.

---

## 4.1 What Is Virtual Memory

Virtual memory is a memory management technique that creates an **illusion** — each process believes it has a large, contiguous, private block of memory, starting at address zero. In reality, the process's memory is:

- Scattered across non-contiguous physical RAM frames
- Partially on disk (swap)
- Shared with other processes (shared libraries, shared memory)
- Lazily allocated (not all virtual pages have physical backing)

```
Process A's View:                   Process B's View:
┌──────────────────┐               ┌──────────────────┐
│ 0x7FFF...  Stack │               │ 0x7FFF...  Stack │
│                  │               │                  │
│ 0x7F00... Libs   │               │ 0x7F00... Libs   │
│                  │               │                  │
│ Heap grows ↑     │               │ Heap grows ↑     │
│ 0x0060... Heap   │               │ 0x0060... Heap   │
│ 0x0040... BSS    │               │ 0x0040... BSS    │
│ 0x0040... Data   │               │ 0x0040... Data   │
│ 0x0040... Text   │               │ 0x0040... Text   │
└──────────────────┘               └──────────────────┘
Both think they have the             But they share physical
entire address space!                memory for libc.so!

                    Physical RAM (shared reality):
                    ┌──────────────────────────────┐
                    │ Frame 42: A's stack page      │
                    │ Frame 57: libc.so page (SHARED)│
                    │ Frame 89: B's heap page        │
                    │ Frame 102: A's heap page       │
                    │ Frame 200: B's stack page      │
                    │ ... scattered everywhere ...    │
                    └──────────────────────────────┘
```

### Why Virtual Memory Exists — The Five Pillars

| Pillar | Purpose | Without VM |
|--------|---------|-----------|
| **Isolation** | Processes can't access each other's memory | Any process could corrupt any other |
| **Abstraction** | Contiguous address space regardless of physical layout | Programs must know physical layout |
| **Overcommit** | Total virtual memory > physical RAM | Limited to physical RAM size |
| **Sharing** | Shared libraries mapped once in RAM | Libraries duplicated per process |
| **Protection** | R/W/X permissions per page | No memory protection |

## 4.2 Virtual vs Physical Addresses

### Virtual Address
- Generated by the CPU when executing instructions
- What the program "sees"
- Translated by the MMU before reaching memory

### Physical Address
- Actual address on the memory bus
- What the DRAM sees
- Determined by the MMU after translation

```c
/* Example: Understanding the difference */
#include <stdio.h>

int global_var = 42;

int main() {
    int local_var = 10;
    int *heap_var = malloc(sizeof(int));
    *heap_var = 20;
    
    printf("Virtual addresses (what the program sees):\n");
    printf("  Code (main):  %p\n", (void*)main);       /* e.g., 0x5555555551a0 */
    printf("  Global:       %p\n", (void*)&global_var); /* e.g., 0x555555558010 */
    printf("  Stack:        %p\n", (void*)&local_var);  /* e.g., 0x7fffffffe3fc */
    printf("  Heap:         %p\n", (void*)heap_var);    /* e.g., 0x5555555592a0 */
    
    /* The physical addresses are completely different! */
    /* Only the kernel and MMU know the physical addresses */
    
    free(heap_var);
    return 0;
}
```

### Viewing the Mapping

```bash
# Virtual to physical mapping via /proc/pid/pagemap
$ cat /proc/self/maps
5555555540000-555555555000 r--p 00000000 08:01 131073  /usr/bin/cat
555555555000-55555555a000 r-xp 00001000 08:01 131073  /usr/bin/cat
7ffff7d80000-7ffff7f17000 r-xp 00025000 08:01 262147  /usr/lib/libc.so.6
7ffffffde000-7ffffffff000 rw-p 00000000 00:00 0       [stack]

# Convert virtual to physical (requires root)
# Uses /proc/pid/pagemap — each virtual page has an 8-byte entry
```

## 4.3 Address Translation Concept

Address translation converts a virtual address to a physical address using page tables.

```
Virtual Address:
┌─────────────────────────────┬──────────────┐
│    Virtual Page Number (VPN)│  Page Offset  │
│         (upper bits)        │ (lower bits)  │
└─────────────────┬───────────┴──────┬────────┘
                  │                   │
                  ▼                   │ (unchanged)
           ┌──────────┐              │
           │Page Table │              │
           │  Lookup   │              │
           └─────┬─────┘              │
                 │                    │
                 ▼                    ▼
┌─────────────────────────────┬──────────────┐
│ Physical Frame Number (PFN) │  Page Offset  │
│      (from page table)      │  (unchanged)  │
└─────────────────────────────┴──────────────┘
                Physical Address

Key insight: The offset within the page is NEVER translated.
Only the page number changes.
```

### Example: 4KB Pages on 48-bit Virtual Address

```
Virtual Address: 0x00007F4A 3B2C 1D5E

Page Offset (bits 0-11):  0xD5E  (12 bits → 4096 byte page)
VPN:                      0x7F4A3B2C1  (36 bits)

After translation:
Physical Frame Number:    0x0001A2B3C  (from page table)
Physical Address:         0x0001A2B3C D5E
                                       ^^^
                                    Offset preserved!
```

## 4.4 Paging vs Segmentation

### Side-by-Side Comparison

```
Segmentation:                          Paging:
┌─────────────┐                       ┌──────────┐
│ Code Segment│ Variable size         │ Page 0   │ Fixed 4KB
│ (2KB)       │                       ├──────────┤
├─────────────┤                       │ Page 1   │ Fixed 4KB
│ Data Segment│ Variable size         ├──────────┤
│ (8KB)       │                       │ Page 2   │ Fixed 4KB
├─────────────┤                       ├──────────┤
│Stack Segment│ Variable size         │ Page 3   │ Fixed 4KB
│ (4KB)       │                       ├──────────┤
└─────────────┘                       │  ...     │
                                      └──────────┘
```

| Feature | Segmentation | Paging | Linux Choice |
|---------|-------------|--------|-------------|
| Unit size | Variable | Fixed (4KB typically) | Paging |
| External fragmentation | Yes | No | Paging wins |
| Internal fragmentation | No | Yes (last page) | Small price |
| Programmer visibility | Visible (segment:offset) | Transparent | Paging wins |
| Protection granularity | Per segment | Per page | Both fine |
| Sharing granularity | Per segment | Per page | Paging more flexible |
| Hardware complexity | Moderate | Lower | Paging wins |
| Used by Linux | Flat model (bypassed) | Primary mechanism | Paging |

### Linux's Decision: Flat Segmentation + Paging

```c
/* Linux sets all segment bases to 0 and limits to max */
/* include/asm/segment.h (x86) */

#define GDT_ENTRY_DEFAULT_USER_CS    5
#define GDT_ENTRY_DEFAULT_USER_DS    6
#define GDT_ENTRY_KERNEL_CS          2
#define GDT_ENTRY_KERNEL_DS          3

/* All segments: base = 0, limit = 0xFFFFF (with granularity = page) */
/* Effectively: virtual address = linear address (segmentation is a no-op) */
/* Then paging translates linear address → physical address */
```

## 4.5 Page Sizes and Page Frames

### Standard Page Size

The default page size on most architectures is **4KB (4096 bytes)**.

```
Why 4KB?
- 12 bits of offset → 2^12 = 4096 bytes
- Good balance between:
  - Table size (smaller pages = larger tables)
  - Internal fragmentation (larger pages = more waste)
  - TLB coverage (larger pages = more coverage per entry)

Page Frame = Physical page-sized block of RAM
Page = Virtual page-sized block of address space
```

### Page Frame Numbers (PFN)

```
Physical Memory:
Address 0x00000000 → PFN 0
Address 0x00001000 → PFN 1   (4KB offset)
Address 0x00002000 → PFN 2
...
Address 0x00100000 → PFN 256  (1MB mark)

Conversion:
PFN = physical_address >> PAGE_SHIFT  (PAGE_SHIFT = 12 for 4KB)
physical_address = PFN << PAGE_SHIFT
```

```c
/* Linux kernel PFN macros */
/* include/linux/pfn.h */

#define PFN_UP(x)    (((x) + PAGE_SIZE - 1) >> PAGE_SHIFT)
#define PFN_DOWN(x)  ((x) >> PAGE_SHIFT)
#define PFN_PHYS(x)  ((phys_addr_t)(x) << PAGE_SHIFT)

/* Convert between struct page and PFN */
/* include/linux/mm.h */
static inline unsigned long page_to_pfn(const struct page *page);
static inline struct page *pfn_to_page(unsigned long pfn);

/* Convert between physical address and struct page */
#define virt_to_page(kaddr) pfn_to_page(__pa(kaddr) >> PAGE_SHIFT)
#define page_to_virt(page)  __va(page_to_pfn(page) << PAGE_SHIFT)
```

### Available Page Sizes

| Architecture | Standard | Large | Huge/Giant |
|-------------|----------|-------|-----------|
| x86_64 | 4KB | 2MB (PMD) | 1GB (PUD) |
| ARM64 (4K granule) | 4KB | 2MB | 1GB |
| ARM64 (16K granule) | 16KB | 32MB | — |
| ARM64 (64K granule) | 64KB | 512MB | — |

## 4.6 Memory Fragmentation

### What Is Fragmentation?

Fragmentation is wasted memory due to how allocation/deallocation patterns leave gaps.

### External Fragmentation

Free memory exists but is scattered in small non-contiguous pieces.

```
Physical RAM (after many alloc/free cycles):
┌──┬────┬──┬──────┬──┬────┬──────┬──┐
│##│FREE│##│ FREE │##│FREE│ FREE │##│
│4K│ 4K │4K│ 8K  │4K│ 4K │ 16K  │4K│
└──┴────┴──┴──────┴──┴────┴──────┴──┘
 ##=allocated

Total free: 4+8+4+16 = 32KB
But can't allocate a contiguous 32KB block!

This is EXTERNAL fragmentation.
```

### Internal Fragmentation

Allocated block is larger than what was requested.

```
Request: 3500 bytes
Allocated: 4096 bytes (1 page = next power-of-2 granularity)
Wasted: 596 bytes (internal fragmentation)

┌────────────────────┬──────────┐
│  Used: 3500 bytes  │ Wasted   │
│                    │ 596 bytes│
└────────────────────┴──────────┘
      One 4KB page
```

---

## 4.7 Internal vs External Fragmentation

| Aspect | Internal Fragmentation | External Fragmentation |
|--------|----------------------|----------------------|
| Definition | Waste inside allocated blocks | Waste between allocated blocks |
| Caused by | Fixed-size allocation units | Variable-size alloc/free patterns |
| In paging | Yes (last page of mapping) | Reduced (same-size pages) |
| In segmentation | No | Yes (variable segment sizes) |
| Linux mitigation | Slab allocator (sub-page alloc) | Buddy allocator + compaction |

### Linux Solutions

```
Internal Fragmentation Solutions:
├── Slab/SLUB allocator: Object caching at sub-page granularity
├── kmalloc: Size-specific caches (32, 64, 128, 256... bytes)
└── Page sub-allocation for small objects

External Fragmentation Solutions:
├── Buddy allocator: Power-of-2 merging reduces fragmentation
├── Memory compaction: Physically moves pages to create contiguous blocks
├── CMA: Reserved contiguous regions for DMA
└── Huge pages: Reduce the number of allocation units
```

## 4.8 Memory Protection

Virtual memory enables fine-grained protection at the page level.

### Protection Levels

```
Per-Page Permissions (set in Page Table Entry):
┌────────┬───────────────────────────────────────┐
│ Bit    │ Meaning                               │
├────────┼───────────────────────────────────────┤
│ Read   │ Page can be read                      │
│ Write  │ Page can be written                   │
│ Execute│ Page can contain executable code       │
│ User   │ Page accessible from user mode         │
│ Kernel │ Page accessible only in kernel mode    │
└────────┴───────────────────────────────────────┘

Typical Linux Mappings:
┌──────────────────┬────────┬───────┬────────┬───────┐
│ Memory Region    │  Read  │ Write │ Execute│ User  │
├──────────────────┼────────┼───────┼────────┼───────┤
│ .text (code)     │   ✓    │   ✗   │   ✓    │   ✓   │
│ .rodata          │   ✓    │   ✗   │   ✗    │   ✓   │
│ .data            │   ✓    │   ✓   │   ✗    │   ✓   │
│ .bss             │   ✓    │   ✓   │   ✗    │   ✓   │
│ Stack            │   ✓    │   ✓   │   ✗    │   ✓   │
│ Heap             │   ✓    │   ✓   │   ✗    │   ✓   │
│ Kernel code      │   ✓    │   ✗   │   ✓    │   ✗   │
│ Kernel data      │   ✓    │   ✓   │   ✗    │   ✗   │
└──────────────────┴────────┴───────┴────────┴───────┘
```

### Protection Violation → Segfault

```c
/* What happens when you violate memory protection */
#include <signal.h>

int main() {
    /* Case 1: Write to read-only memory → SIGSEGV */
    const char *str = "hello";
    str[0] = 'H';  /* SEGFAULT! .rodata is read-only */
    
    /* Case 2: Execute data → SIGSEGV (NX bit) */
    char code[] = { 0xC3 };  /* RET instruction */
    void (*func)(void) = (void(*)(void))code;
    func();  /* SEGFAULT! Stack is not executable */
    
    /* Case 3: Access kernel memory from user space → SIGSEGV */
    int *kernel_ptr = (int *)0xFFFF800000000000UL;
    int val = *kernel_ptr;  /* SEGFAULT! Kernel pages not accessible */
    
    return 0;
}
```

## 4.9 Shared Memory Concepts

Virtual memory enables efficient sharing of physical memory between processes.

### Types of Sharing in Linux

```
1. Shared Libraries (.so files):
   Process A: VA 0x7F000000 ─┐
                              ├──→ Physical Frame 500 (libc.so .text)
   Process B: VA 0x7F100000 ─┘
   
   Same physical page, different virtual addresses!
   Read-only sharing (code pages) — very safe.

2. Shared Memory (POSIX shm, SysV shm):
   Process A: VA 0x7F200000 ─┐
                              ├──→ Physical Frame 800 (shared data)
   Process B: VA 0x7F300000 ─┘
   
   Read-write sharing — processes must synchronize!

3. Copy-on-Write (fork):
   Parent: VA 0x600000 ─┐
                         ├──→ Physical Frame 300 (shared, R/O)
   Child:  VA 0x600000 ─┘
   
   Both point to same frame (read-only).
   On write by either → frame is copied, each gets its own.

4. Memory-Mapped Files (mmap MAP_SHARED):
   Process A: VA 0x7F400000 ─┐
                              ├──→ Physical Frame 900 (file page)
   Process B: VA 0x7F500000 ─┘
   
   Changes visible to both processes and written back to file.
```

```c
/* POSIX Shared Memory Example */
#include <sys/mman.h>
#include <fcntl.h>

/* Create shared memory */
int fd = shm_open("/my_shm", O_CREAT | O_RDWR, 0666);
ftruncate(fd, 4096);
void *ptr = mmap(NULL, 4096, PROT_READ | PROT_WRITE,
                 MAP_SHARED, fd, 0);

/* ptr is now shared between all processes that map /my_shm */
```

## 4.10 Memory Isolation Between Processes

### How Isolation Works

Each process has its **own page table** (pointed to by CR3 on x86 or TTBR0 on ARM64). This means:

1. Process A's virtual address 0x1000 maps to physical frame X
2. Process B's virtual address 0x1000 maps to physical frame Y
3. Neither can see the other's mappings

```
Process A's Page Table:              Process B's Page Table:
VA 0x1000 → PF 500                  VA 0x1000 → PF 800
VA 0x2000 → PF 501                  VA 0x2000 → PF 350
VA 0x3000 → PF 502                  VA 0x3000 → PF 999

Context Switch A→B:
1. Save A's register state
2. Load CR3 with B's page table base (different physical address!)
3. TLB entries for A become invalid (unless ASIDs used)
4. Load B's register state
5. Resume B — now MMU uses B's page tables
```

```c
/* Linux context switch — loading new page tables */
/* arch/x86/mm/tlb.c */

void switch_mm_irqs_off(struct mm_struct *prev,
                        struct mm_struct *next,
                        struct task_struct *tsk)
{
    /* ... */
    if (prev != next) {
        /* Load new CR3 — switches the entire address space */
        load_new_mm_cr3(next->pgd, new_asid, true);
    }
    /* ... */
}
```

### Kernel Space Sharing

While user space is isolated per process, **kernel space is shared** across all processes:

```
┌─────────────────────────────────┐ 0xFFFFFFFFFFFFFFFF
│      Kernel Space               │
│  (Same mapping in ALL processes)│  ← Shared page tables
├─────────────────────────────────┤ 0xFFFF800000000000
│                                 │
│      User Space                 │
│  (Different per process)        │  ← Each process has its own
│                                 │
└─────────────────────────────────┘ 0x0000000000000000
```

This is achieved by making the kernel portion of all process page tables point to the same kernel page table entries. On ARM64, this is cleaner — TTBR0 (user) switches per process, TTBR1 (kernel) stays the same.

## Flow Diagram: Virtual Memory in Action

```
Program executes: int x = array[100];

Step 1: CPU generates virtual address
        VA = base_of_array + 100 * sizeof(int) = 0x7FFE12345678

Step 2: MMU checks TLB
        ├── TLB Hit → Physical address immediately → Cache/RAM access
        └── TLB Miss → Step 3

Step 3: Hardware Page Table Walk
        PML4[idx] → PDPT[idx] → PD[idx] → PT[idx] → PTE
        ├── PTE Present bit = 1 → Extract PFN, fill TLB → Cache/RAM
        └── PTE Present bit = 0 → Step 4

Step 4: Page Fault Exception (#PF on x86)
        CPU saves state, jumps to Linux page fault handler
        ├── Valid mapping but page not loaded → Demand paging
        │   └── Allocate physical frame, load data, update PTE → Resume
        ├── Valid mapping but protection violation → Handle CoW or SEGFAULT
        └── Invalid mapping (no VMA) → SIGSEGV → Process killed
```

## Interview Questions

1. **Q: What is virtual memory and why is it necessary?**
   A: Virtual memory provides each process with an isolated, contiguous address space. It's necessary for: process isolation (security), address space abstraction (simplifies programming), overcommit (use more memory than RAM), and sharing (libraries, IPC).

2. **Q: Explain the difference between a page and a frame.**
   A: A page is a fixed-size block of virtual address space. A frame (or page frame) is a fixed-size block of physical memory. The page table maps pages to frames.

3. **Q: Why did Linux choose paging over segmentation?**
   A: Paging eliminates external fragmentation, is transparent to programs, has simpler hardware support, and enables efficient swapping. Linux uses a flat segmentation model (base=0, limit=max) and relies entirely on paging.

4. **Q: How does Linux achieve process isolation?**
   A: Each process has its own page table (pointed to by CR3/TTBR0). On context switch, the page table base is reloaded, making the previous process's user-space mappings invisible. Hardware (MMU) enforces this — no software bypass possible.

5. **Q: What causes a segmentation fault?**
   A: A segfault (SIGSEGV) occurs when a process accesses memory it doesn't have permission for: unmapped addresses, writing to read-only pages, executing non-executable pages, or accessing kernel memory from user space.

6. **Q: How is memory shared between processes in Linux?**
   A: Through shared memory mappings (shmget/mmap MAP_SHARED), shared libraries (same physical pages mapped read-only into multiple processes), memory-mapped files, and copy-on-write after fork().

---

## Summary & Key Takeaways

1. Virtual memory gives each process the illusion of a large, private, contiguous address space.
2. The MMU translates virtual addresses to physical addresses using page tables — the offset within a page is never translated.
3. Linux uses paging (not segmentation) as its primary address translation mechanism.
4. Pages are fixed-size (typically 4KB) virtual memory units; frames are the physical counterparts.
5. Memory protection is per-page: read, write, execute, user/kernel permissions enforced by hardware.
6. Processes are isolated by having separate page tables; context switches load new page table bases.
7. Sharing is achieved through mapping the same physical frames into multiple processes' page tables.
8. Memory fragmentation is managed through the buddy allocator (external) and slab allocator (internal).
