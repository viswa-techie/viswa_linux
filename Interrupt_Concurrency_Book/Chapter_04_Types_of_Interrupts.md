## Learning Goals
- Classify all interrupt types in the Linux kernel

- See how each type maps to Linux kernel handling paths
- Recognize which types you'll encounter in driver development

## 4.1 Hardware Interrupts

### Definition

Hardware interrupts are **asynchronous signals** generated by external devices to request CPU attention. They arrive unpredictably relative to the currently executing code.

```
  ┌────────────┐     electrical    ┌─────────────────┐
  │ Device     │ ───signal/msg───→ │ Interrupt        │
  │ (NIC, UART,│                   │ Controller       │
  │  GPIO, DMA)│                   │ (APIC/GIC)       │
  └────────────┘                   └────────┬─────────┘
                                            │
                                    ┌───────▼────────┐
                                    │   CPU Core     │
                                    │ (checks b/w    │
                                    │  instructions) │
                                    └────────────────┘
```

### Key Characteristics

```
- Asynchronous: Arrive at ANY time during execution
- External: Generated by hardware, not by program
- Maskable: Most can be disabled (except NMI)
- Vectored: Each has a vector number for handler lookup
- Context: Handler runs in "interrupt context" (cannot sleep)
```

### Common Sources in Embedded/SoC

```
Source           │ IRQ Type      │ Typical Usage
─────────────────┼───────────────┼──────────────────────────
Network card     │ MSI-X / SPI   │ Packet arrival, TX complete
UART             │ SPI           │ Byte received, TX empty
GPIO pin         │ SPI/PPI       │ Button press, sensor alert
DMA controller   │ SPI           │ Transfer complete
I2C/SPI bus      │ SPI           │ Transaction complete
Watchdog timer   │ PPI/SPI       │ Timeout warning
USB controller   │ SPI           │ Device connect/disconnect
Display/GPU      │ SPI           │ Vsync, page flip complete
Audio codec      │ SPI           │ Buffer underrun/overrun
Camera (ISP)     │ SPI           │ Frame captured
```

## 4.2 Software Interrupts

### Definition

Software interrupts are **synchronous events** triggered by executing specific instructions. They are intentional — the program deliberately invokes them.

```
Types of software interrupts:

1. System Calls (most common):
   x86:  INT 0x80 (legacy), SYSCALL (modern)
   ARM:  SVC instruction → Supervisor Call → EL1
   Used by: user programs to request kernel services

2. Software Interrupt Instructions:
   x86:  INT n (trigger vector n)
   ARM:  SWI / SVC

3. Linux SoftIRQs (kernel concept, NOT hardware):
   Confusingly named! These are deferred work mechanism,
   NOT hardware software interrupts.
   Covered in detail in Chapter 8.
```

### System Call Path

```
User Process                    Kernel
──────────                      ──────
write(fd, buf, len)
  │
  ▼
glibc wrapper
  │
  ▼
SYSCALL instruction ──────────→ entry_SYSCALL_64 (x86)
  (or SVC on ARM)               el0_svc (ARM64)
                                  │
                                  ▼
                               sys_write()
                                  │
                                  ▼
                               vfs_write()
                                  │
                                  ▼
                               Return to user
```

## 4.3 Exceptions

### Definition

Exceptions are **synchronous events** generated by the CPU itself when it encounters an error or special condition during instruction execution.

```
Exception Categories:

1. Faults (recoverable, restart instruction):
   - Page Fault (#PF, vector 14): Access unmapped page
     → Kernel maps the page, re-executes instruction
   - Segment Not Present (#NP, vector 11)

2. Traps (recoverable, continue after instruction):
   - Breakpoint (#BP, vector 3): INT3 instruction
     → Debugger handles, continues from next instruction
   - Overflow (#OF, vector 4): INTO instruction

3. Aborts (unrecoverable):
   - Double Fault (#DF, vector 8): Exception during exception
   - Machine Check (#MC, vector 18): Hardware failure
     → Usually kernel panic
```

### x86 Exception Vectors (0-31)

```
Vector │ Mnemonic │ Description              │ Type
───────┼──────────┼──────────────────────────┼────────
0      │ #DE      │ Divide Error             │ Fault
1      │ #DB      │ Debug                    │ Trap/Fault
2      │ NMI      │ Non-Maskable Interrupt   │ Interrupt
3      │ #BP      │ Breakpoint               │ Trap
4      │ #OF      │ Overflow                 │ Trap
5      │ #BR      │ Bound Range Exceeded     │ Fault
6      │ #UD      │ Invalid Opcode           │ Fault
7      │ #NM      │ Device Not Available     │ Fault
8      │ #DF      │ Double Fault             │ Abort
10     │ #TS      │ Invalid TSS              │ Fault
11     │ #NP      │ Segment Not Present      │ Fault
12     │ #SS      │ Stack Segment Fault      │ Fault
13     │ #GP      │ General Protection       │ Fault
14     │ #PF      │ Page Fault               │ Fault
18     │ #MC      │ Machine Check            │ Abort
```

### ARM64 Exceptions

```
ARM64 uses Exception Level transitions:

Exception Type     │ Cause                    │ Handler
───────────────────┼──────────────────────────┼─────────────
Synchronous        │ SVC, data/inst abort,    │ el1_sync
                   │ SP alignment, BRK        │ (from EL1)
IRQ                │ External HW interrupt    │ el1_irq
FIQ                │ Fast interrupt (secure)  │ el1_fiq
SError             │ Async external abort     │ el1_error

Data Abort (ESR_EL1 analysis):
  Instruction Specific Syndrome (ISS) provides:
  - Fault type (translation, permission, alignment)
  - Access level, write/read
  - Far address (FAR_EL1 = faulting address)
```

## 4.4 Non-Maskable Interrupts (NMI)

### Purpose

NMI cannot be disabled by normal interrupt masking (CLI on x86, DAIF on ARM). Used for critical events that must always be serviced.

```
NMI Use Cases:
  ┌─────────────────────────┬─────────────────────────────┐
  │ Use Case                │ Why NMI?                    │
  ├─────────────────────────┼─────────────────────────────┤
  │ Hardware failure        │ Must report even if IRQs off│
  │ Watchdog timeout        │ Detect lockups              │
  │ Performance profiling   │ Sample even in IRQ-disabled │
  │ Kernel crash dump       │ Stop CPUs during panic      │
  │ Machine check           │ Hardware error notification │
  │ Debug (SysRq)           │ Break into locked system    │
  └─────────────────────────┴─────────────────────────────┘
```

### NMI in Linux

```c
/* Linux NMI watchdog: detects hard lockups */
/* A CPU that doesn't respond to timer IRQ for >N seconds
   triggers NMI watchdog → kernel panic or backtrace */

/* View NMI counts: */
$ cat /proc/interrupts | grep NMI
NMI:       1234       1233       1235       1234   Non-maskable interrupts

/* NMI handler registration (x86): */
register_nmi_handler(NMI_LOCAL, my_nmi_handler, 0, "mymod");

/* CRITICAL: NMI handler is extremely restricted:
   - Cannot take ANY lock (might deadlock if lock was held)
   - Cannot access most kernel services
   - Must use NMI-safe operations only
   - Uses raw_spin_trylock (never spin) */
```

## 4.5 Maskable Interrupts

```
Maskable interrupts: Can be temporarily disabled by software.
This is the NORMAL type of device interrupt.

Masking hierarchy:
  ┌─────────────────────────────────────────────┐
  │ 1. CPU-level: local_irq_disable()           │
  │    Disables ALL maskable IRQs on this CPU    │
  │    Used by spinlock_irqsave                  │
  ├─────────────────────────────────────────────┤
  │ 2. Controller-level: disable_irq(irq)        │
  │    Disables ONE specific IRQ on ALL CPUs     │
  │    Used for per-device control               │
  ├─────────────────────────────────────────────┤
  │ 3. Device-level: write to device register    │
  │    Disables interrupt generation at source   │
  │    Driver-specific                           │
  └─────────────────────────────────────────────┘

When to mask:
  - Protecting critical sections from interrupt interference
  - During device reconfiguration
  - spin_lock_irqsave() automatically masks on local CPU
  
When NOT to mask:
  - For extended periods (increases latency)
  - Globally when only local masking needed
  - In bottom halves (wrong context)
```

## 4.6 Inter-Processor Interrupts (IPI)

### Definition

IPIs are interrupts sent from one CPU to another CPU in an SMP system. Used for kernel coordination, not device I/O.

```
  CPU 0                        CPU 1
  ┌────────┐   IPI message    ┌────────┐
  │        │ ───────────────→ │        │
  │ Sender │                  │ Handler│
  │        │                  │        │
  └────────┘                  └────────┘
  smp_call_function()          IPI handler executes

ARM: SGI (Software Generated Interrupt) IDs 0-15
x86: LAPIC ICR (Interrupt Command Register) write
```

### Common IPI Uses in Linux

```
IPI Purpose          │ Function                    │ Explanation
─────────────────────┼─────────────────────────────┼──────────────────
TLB shootdown        │ flush_tlb_others()          │ Invalidate TLB
                     │                             │ on remote CPUs
Reschedule           │ smp_send_reschedule()       │ Tell CPU to run
                     │                             │ scheduler
Function call        │ smp_call_function()         │ Execute function
                     │ smp_call_function_single()  │ on another CPU
Stop CPU             │ smp_send_stop()             │ Halt for panic
Timer sync           │ (clock synchronization)     │ Keep TSCs aligned
RCU                  │ (grace period detection)    │ Expedite callbacks
```

## 4.7 Timer Interrupts

### Purpose

Timer interrupts drive the kernel's notion of time, enabling scheduling, timeouts, and timekeeping.

```
Timer Interrupt Sources:

x86:
  - PIT (8254): Legacy, 1.193182 MHz, IRQ 0
  - HPET: High Precision Event Timer
  - LAPIC Timer: Per-CPU, most commonly used
  - TSC Deadline: Precise, TSC-based wakeup

ARM:
  - ARM Generic Timer: Per-CPU, PPI ID 27 (phys), 30 (virt)
  - External timer: SoC-specific
```

### Timer IRQ Role

```
Timer tick fires → scheduler_tick():
  │
  ├── Update jiffies (global tick count)
  ├── Update process runtime (accounting)
  ├── Check time slices (CFS vruntime update)
  ├── set TIF_NEED_RESCHED if preemption needed
  ├── Run expired hrtimers
  ├── Process POSIX timers
  └── Drive RCU callbacks
```

### Tickless Kernel (NO_HZ)

```
Traditional: Timer fires every 1ms/4ms/10ms (CONFIG_HZ)
  ────┬────┬────┬────┬────┬────┬────┬────→ time
      │tick│tick│tick│tick│tick│tick│tick

Tickless (NO_HZ_IDLE): Stop ticks when CPU is idle
  ────┬────┬─────────────────────┬────→ time
      │tick│tick     (idle, no ticks)    │tick

Tickless (NO_HZ_FULL): Stop ticks even when one task runs
  ────┬─────────────────────────────→ time  
      │tick  (single task, no overhead)

Benefit: Power savings, reduced overhead for idle/busy CPUs
```

## 4.8 Device Interrupts

### The Most Common Type in Driver Development

```
Device interrupts are hardware IRQs from peripheral devices:

Registration:
  int ret = request_irq(irq_num, handler, flags, name, dev);

Flags:
  IRQF_SHARED       ← Multiple devices share this IRQ line
  IRQF_ONESHOT       ← Keep IRQ masked until thread completes
  IRQF_TRIGGER_*     ← Edge/level trigger type
  IRQF_NO_SUSPEND    ← Don't disable during system suspend
  IRQF_NO_THREAD     ← Never convert to threaded (PREEMPT_RT)

Typical driver pattern:
  static irqreturn_t my_handler(int irq, void *dev_id)
  {
      struct my_device *dev = dev_id;
      u32 status = readl(dev->regs + INT_STATUS);
      
      if (!(status & MY_DEVICE_IRQ))
          return IRQ_NONE;  /* Not our interrupt (shared) */
      
      writel(status, dev->regs + INT_CLEAR);  /* Ack hardware */
      
      /* Schedule bottom half for heavy processing */
      tasklet_schedule(&dev->tasklet);
      
      return IRQ_HANDLED;
  }
```

## Complete Interrupt Taxonomy

```
                    Interrupts
                    ─────────
         ┌──────────────┴──────────────┐
     Synchronous                   Asynchronous
     (CPU generates)               (External)
         │                              │
    ┌────┴────┐                ┌────────┴────────┐
 Exceptions  Software       Hardware          IPI
    │        Interrupts     Interrupts        │
    │        (SVC/INT)      │                 │
    │                       │                 └─ Reschedule
    ├─ Faults              ├─ Maskable            TLB flush
    │  (#PF, #GP)          │  (device IRQs)       Function call
    │                      │                      Stop
    ├─ Traps               ├─ NMI
    │  (#BP, #OF)          │  (watchdog, MCE)
    │                      │
    └─ Aborts              ├─ Timer
       (#DF, #MC)          │  (jiffies, hrtimer)
                           │
                           └─ Device
                              (NIC, UART, GPIO,
                               DMA, USB, etc.)
```

## Linux Handling Path Per Type

```
Type              │ Entry Point              │ Context
──────────────────┼──────────────────────────┼──────────────
Hardware IRQ      │ do_IRQ() / handle_IRQ()  │ hardirq
NMI               │ nmi_handler              │ NMI (most restricted)
Exception (fault) │ do_page_fault(), etc.    │ exception
System call       │ do_syscall_64() /        │ process context
                  │ el0_svc_handler()        │
Timer             │ scheduler_tick() via     │ hardirq
                  │ timer IRQ handler        │
IPI               │ smp_*_interrupt()        │ hardirq
SoftIRQ           │ __do_softirq()           │ softirq context
```

## Summary

- Hardware interrupts are external, asynchronous device signals — the driver developer's bread and butter
- Software interrupts (SVC/INT) implement system calls
- Exceptions are synchronous CPU faults/traps (page fault is the most important for memory management)
- NMI cannot be masked — used for watchdogs, profiling, crash recovery
- IPIs coordinate between CPUs in SMP (TLB shootdown, rescheduling)
- Timer interrupts drive scheduling, timekeeping, and deferred work
- Each type has a different entry path and execution context in the kernel
